## Principles
Deterministic engines separated from UI. No LLM at runtime. No invented regulations (unverifiable -> "REGULATION COULD NOT BE VERIFIED"). No guessing missing inputs. Demo data always labelled and never mixed with production records.

## Key decisions
- **Hash routing** (`#/map`): works on any static host and offline without server rewrites.
- **Router is a pure table** (`routes.ts`) so it is unit-testable without React.
- **Storage envelope** `{v, t, d}`; unsupported versions raise `StorageError` with a specific message. Prefix `eca-pilot:`. `createStore()` falls back to memory when localStorage is blocked.
- **Planned DB** (Chunk 03+): IndexedDB behind the same async interface style; see `DATABASE_SCHEMA.md`.
- **Map provider** (Chunk 05): Leaflet-style provider behind a replaceable `MapProvider` interface; `.env.example` has `VITE_MAP_PROVIDER`.
- **Version/dataset**: `REGULATION_DATASET_VERSION` is `null` until real data exists.
- **Capacitor readiness**: no browser-only assumptions beyond service worker/geolocation, which sit behind service modules.

- **Profile validation is pure** (`validateProfile(profile, now)`); issues carry `path`, `section`, `kind` (missing/invalid), a specific message and a "why it matters" reason. The UI only renders them. Paths (`mainEngine.ratedPowerKw`, `auxiliaryEngines.1.ratedRpm`) bind issues to inline fields.
- **Missing vs invalid vs not applicable**: "" / null / "unknown" = missing; out-of-range or malformed = invalid (blocks Save); "not_applicable" = answered. Missing values never block Save (partial progress is kept) but keep the profile INCOMPLETE.
- **Profile persistence**: strict parser, no repair, no migration yet (only schemaVersion 1). A future schema change must add an explicit migration.
- **Header chip / Dashboard** read the SAVED profile via `useVesselStatus` (refreshed by the `eca:vessel-profile-changed` window event).

- **FOBAS engine is pure** and returns `{ok:true,...steps}` or `{ok:false,errors[]}` with field paths; the screen only renders. Units are converted to a common base (kg or m³, per hour); density is used only when bases differ and is never defaulted.
- **Calculator prefill** reads the SAVED vessel profile through `prefillFromProfile` (pure). Prefilled values are visibly marked and editable; nothing is prefilled from an unreadable profile. The calculator stores nothing.

- **Regulation data is validated, never trusted**: `parseDataset(raw, now)` is pure and strict. Dataset-level problems reject the whole dataset; record-level problems reject only that record (listed with reasons). Nothing is repaired, defaulted or fetched from the network.
- **DEMO isolation**: demo and production are separate datasets with a mandatory `isDemo` flag, `DEMO-` id prefix rules enforced both ways, DEMO freshness always UNVERIFIED, and a DEMO dataset supplied as production is rejected. No engine may consume DEMO records.
- **No dataset = no rule**: while `BUNDLED_PRODUCTION` is `null` the UI says "REGULATION COULD NOT BE VERIFIED". `REGULATION_DATASET_VERSION` stays `null` until real verified content is supplied.
- **Freshness thresholds** are exposed constants marked `confirmed: false`; the UI says so.

- **Geo engine is pure and lives in `src/calculations/geo/`**; `src/map/` stays reserved for the map UI (Chunk 05). Models carry no behaviour.
- **Strict area parsing**: `parseArea` rejects, never repairs; errors carry a path and a readable message. DEMO ids must start with `DEMO-` and production ids must not.
- **Antimeridian**: coordinates stay in [-180, 180]; rings/tracks are unwrapped (consecutive vertices <= 180 degrees apart) and queries shifted by multiples of 360. Pole-enclosing polygons are rejected. Edges are straight in lon/lat space; distances are haversine (R = 6371008.8 m, a stated assumption).
- **Three-state point test**: INSIDE / OUTSIDE / BOUNDARY (tolerance 1e-9 degrees). The engine never silently resolves a boundary point.
- **Scope isolation**: `evaluatePosition(position, areas, scope)` and `nextAreaAlongTrack(...)` take `"REAL"` (default; DEMO areas ignored) or `"DEMO"` (explicit; only DEMO areas). No areas in scope = `UNKNOWN_NO_AREA_DATA`, never OUTSIDE. The engine gives no regulatory meaning to an area `type`.
- **Next area** uses the projected track AHEAD of the vessel (position is prepended); only areas the position is clearly OUTSIDE of are candidates; nearest first entry wins.

- **Map = renderer of engine output.** `MapProvider` (interface) owns the scene; `SvgMap` draws a snapshot via `useSyncExternalStore`. The map never classifies a point or computes a distance. A tile/Leaflet provider can be added behind the same interface; `VITE_MAP_PROVIDER` selects it (only `svg` exists, anything else is reported and falls back).
- **No basemap on purpose**: only a lat/lon graticule is drawn. No coastlines, ports or charts exist in the app, so none are invented. Offline behaviour is therefore complete (no network requests).
- **Drawing antimeridian rule**: paths and polygons are unwrapped with the engine's `unwrap` and shifted by a multiple of 360 into the copy nearest the view centre; holes are aligned to the outer ring first. View centre wraps with `wrap180`.
- **DEMO on the map**: DEMO layer off by default; DEMO areas get dashed outline, hatch and a text "(DEMO)" label; the mock scene uses scope `DEMO` only when that layer is on, so hidden DEMO data never produces a marker or result.
- **Vessel on the map** is drawn ONLY from the GPS state (`map/gpsVessel.ts`: `vesselFromGps`). The Chunk 05 component-state mock position is gone; the developer panel now feeds the labelled MOCK GPS source instead. Its projected track / DEMO entry marker still use `buildMockScene` + `applyMockScene(p, scene, false)` (the `false` leaves the vessel alone).

- **GPS pipeline** (Chunk 06): `source` (device or mock) emits RAW fixes -> `store` validates with `acceptFix` (pure) -> `buildGpsState` (pure) -> immutable `GpsState` snapshot -> `useGps()` -> header chip, `GpsPanel`, map. A source never repairs a value; the only conversion is the Geolocation API's own "no value" (`null` / `NaN`) -> `null` (not reported). Nothing becomes 0.
- **Reliability vocabulary**: NO_FIX, ACQUIRING, GOOD, DEGRADED (accuracy worse than limit or unreported), STALE (older than limit), INVALID (latest fix rejected, position not shown), DENIED, UNAVAILABLE, MOCK. Boundaries: exactly at the stale or accuracy limit is NOT stale / NOT degraded. STALE outranks DEGRADED.
- **Drawable states**: GOOD, DEGRADED, STALE, MOCK. STALE shows the last known position with a text tag and age; NO_FIX, ACQUIRING, INVALID, DENIED, UNAVAILABLE show the NO POSITION badge. Tags are text ("MOCK", "STALE 1 min 00 s", "DEGRADED"); dashed outline is an extra cue only.
- **MOCK can never pass as device GPS**: the mock source overwrites `source` with `"mock"`; the store rejects (`SOURCE_MISMATCH`) any fix whose source differs from the running source; a mock fix gives reliability MOCK (or STALE, still marked mock). The header chip reads "GPS MOCK (NOT GPS)".
- **Rejections**: non-finite/out-of-range position (reuses `validatePoint`), bad timestamp, timestamp more than the skew tolerance in the future, negative or non-finite accuracy/speed, non-finite heading, speed above the plausible maximum, and jumps (implied speed after subtracting both accuracy radii above the plausible maximum). A rejected fix makes the state INVALID; the last accepted fix stays as the baseline (not shown), so the next plausible fix recovers and a long gap lowers the implied speed. A fix not newer than the last accepted one is IGNORED with a notice (not an error).
- **SOG/COG**: device values first (SOG m/s -> kn with 1852 m/NM; COG normalised to [0,360)). If absent, derived from the last accepted fix only if the interval is within [min,max] s (COG also needs a minimum distance); flagged DERIVED in state and UI; otherwise null with a stated reason. Geolocation `heading` is treated as course over ground (direction of travel), not a compass heading.
- **Thresholds** (`GPS_THRESHOLDS`) are exposed constants with `confirmed: false`, displayed on Settings as an UNCONFIRMED PROPOSAL. Stale 30 s, poor accuracy 50 m, max plausible speed 50 kn, clock skew 5 s, derived interval 5 to 120 s, derived COG min distance 20 m.
- **Permission** is requested only when the user presses "Start device GPS" (never on load). Needs HTTPS or localhost; an insecure context or missing API gives UNAVAILABLE with the reason. A re-evaluation timer (1 s) exists only while a source is active, so a silent receiver turns STALE by the clock alone. Callbacks from a stopped or replaced source are ignored (token).
- **No position history**: no track buffer was added; the Track layer still has no data source (label now "Track (not recorded yet)").

## SOx rules layer (Chunk 08)
- `models/sox.ts` (types, reason codes) -> `calculations/sox/engine.ts` (pure `selectSox`, takes the date and the loaded dataset as arguments, no clock, no React) -> `hooks/useSox.ts` (scope from the DEMO switch, today's date, bundled dataset) -> `components/SoxPanels.tsx`.
- The engine contains no regulatory number. It reuses `timeStateProblem` (validation.ts) and `evaluateFreshness` (loader.ts) rather than copying them.
- Scope: `DEMO` reads only a DEMO dataset (`demoSox`, built from `now`); `REAL` reads the production dataset, which is `null`, so it refuses with NO_DATASET.
- Selection policy (design points, UNCONFIRMED PROPOSAL): records must be CURRENT on the query date with freshness VERIFIED CURRENT or UPDATE RECOMMENDED (flag); several usable matches are never resolved (CONFLICT - VERIFY). A GLOBAL record matches every area, so it conflicts with a usable AREA record by design.
- Limitations: see `PROJECT_CHECKPOINT.md` (the single list).

## Port advisor layer (Chunk 10)
- `models/port.ts` -> `services/ports/` (strict parser: `parsePortList`, `parsePortListJson`) -> `calculations/port/engine.ts` (pure `adviseForPort`). Reuses `gateQuery`, `judgeAll` and the SOx / NOx-PM entry builders (`soxEntry`, `noxPmEntry`) so port entries are identical to the layer entries.
- Gates, in a fixed order: bad date, no / unreadable port list, scope vs list (REAL + DEMO list = NO_DATASET + DATASET_DEMO_ONLY), no port picked, port not in the list (a rejected port is PORT_NOT_FOUND), port verification (STALE or after the query date = PORT_UNVERIFIED). Past the gates the advice is OK and each section (topic SOX | NOX | PM x origin PORT | AREA) answers or refuses on its own; OK never means a rule was found.
- Origin PORT = blocks with basis PORT naming the port id. Origin AREA (only when the port has an `areaId`) = blocks with basis AREA or GLOBAL for that area; a PORT-basis block never counts as area-level and an AREA-basis block never as port-level.
- No port, rule text or number of its own: every value is copied from the port list, a record or a fixed status string; every advice carries `VERIFY WITH PORT / AUTHORITY`. No ETA, route or GPS lookup; the port is only ever chosen by the user.
- Scope: `DEMO` reads the DEMO port list and DEMO datasets (built from `now`); `REAL` reads only an imported, ACTIVE production port list and dataset (Chunk 11B) and refuses with NO_DATASET when none is loaded.
- UI (10B): `hooks/usePort.ts` (bundled DEMO list and datasets loaded once, scope DEMO) -> `components/PortPanels.tsx` -> `screens/PortScreen.tsx` (`#/port`) and the Dashboard `PortDashboardPanel`. The chosen port id is a session-only module store (`portChoice`, read with `useSyncExternalStore`): never written to storage, null by default, cleared by a reload, shared by the Dashboard panel and the Port screen. The components render the advice as data (reason codes shown verbatim) and add no wording of their own beyond fixed labels; entries are grouped by origin ("Entries for this port" / "Entries for the port's area").
- Regulation Center lists the DEMO ports and the PORT-basis blocks of the DEMO records; Settings shows `PORT_DESIGN_POINTS` as UNCONFIRMED PROPOSAL (five "Confirmed: NO" lines on Settings now).
- Limitations: see `PROJECT_CHECKPOINT.md` (the single list).

- **Area queries accept AREA / GLOBAL blocks only (Chunk 11)**: a block with basis PORT names a port id in `areaId` and answers port-level queries only. The SOx and NOx / PM area queries ignore PORT blocks; the port engine takes PORT blocks for the port and non-PORT blocks for the port's area. The two sides cannot answer each other's queries even if ids collide.
- **Imported data is a separate source, never mixed (Chunk 11A)**: `loadAll(now, store)` = bundled DEMO data + the ACTIVE imported production data. Imports are user-supplied files parsed by the same strict parsers; versions are immutable; activation is an explicit, recorded user action (an import never activates); nothing active = `production` null = REAL scope refuses with NO_DATASET. DEMO files are never importable and the production slot never holds DEMO data.
- **Store behind an interface**: `VersionStore` (memory or key-value implementation share one code path) with specific error codes; format versions are explicit and an unknown one is an error, not a repair.

## Alerts layer (Chunk 12)
- `models/alerts.ts` -> `calculations/alerts/engine.ts` (pure `evaluateAlert`, clock injected) -> `calculations/alerts/notifications.ts` (pure `recordEvaluation` / `acknowledge`). The engine reads only outputs the app already computes: `GpsState` (through the prediction's `gpsUsability`), `PredictionResult`, `CurrentAreaAssessment`, `RegulationStatus` and `ProfileStatus` (as structural subsets), and user-entered lead times. It computes no geometry, no ETA and no duration of its own.
- Output: one `OperationalStatus`, one `AlertLevel`, `reasons[]` (DETERMINING first, NOTE after), `demo`, `mock`, `timing` (kept on VERIFY results too). Priority: GPS UNRELIABLE, STALE DATA, VERIFY, INSIDE ECA, timing (WINDOW ACTIVE, SOON, PREPARE), NORMAL. Missing or unreliable input is never NORMAL. In REAL scope with no active imported boundary set the result is VERIFY with `NO_AREA_DATA` and says so; with an UNVERIFIED or unreadable set it is VERIFY with `AREA_DATA_UNVERIFIED` / `AREA_DATA_UNREADABLE` (Chunk 16).
- Lead times have no default; a null lead time means "not evaluated" and is listed. A passed latest start time is a fact of the prediction and needs no lead time. ENTRY IMMINENT, EXIT APPROACHING and EXITED are not produced (listed in `NOT_PRODUCED_STATUSES`).
- Notifications are a pure state value (`NotificationState`), not a service: no timer, no storage, no network, no push. Layer rule checked by a test: the alert sources in `calculations/alerts` import nothing from services, hooks, components or screens.
- **12B wiring**: `services/alerts/store.ts` is a session-only module store (same pattern as `services/prediction/inputsStore.ts`) holding the lead-time texts + parsed lead times, the `NotificationState` and the latest evaluation. `AlertsRunner` (mounted once in `AppShell`, renders nothing) is the ONLY place that builds the `AlertInput` from `useGps()`, `usePrediction()`, `useData().data?.status` and `useVesselStatus()`, calls `evaluateAlert(Date.now())` in a `useEffect` and `submit`s the result. It subscribes to `leadTimes` only, so its own output cannot re-trigger it; `leadTimes` / `leadTexts` keep their identity until the user edits, and `recordEvaluation` returns the same `NotificationState` object for an unchanged state, so the GPS tick (1 s) never creates an entry or a render loop.
- UI: `AlertPanels` (Dashboard OPERATIONAL STATUS with the lead-time fields; `alertChip` for the header), `NotificationPanels` (banner + ALERT LIST on the Dashboard), the header chip in `AppShell`, the Settings panel. Everything is read through `useAlerts()`. Lead times and the list are session only (no key in `DATABASE_SCHEMA.md`); they are not a record, the Chunk 13 log is its own persisted data.

CSV: `buildCsv`; the download carries a UTF-8 byte-order mark, the CSV text does not. XLSX does not exist.

## Offline-first and storage (Chunk 14)
- **Service worker**: cache `eca-pilot-v<version>-<fingerprint>`; install precaches ALL built files (all-or-nothing, no `skipWaiting`); precached files cache-first; navigation falls back to cached `index.html`; no other request is touched or cached; old caches removed on activate. The page (`register.ts`) shows a waiting worker as "new version ready" and only the user's button sends SKIP_WAITING. The app itself makes no network request.
- **Storage errors**: every `KeyValueStore` failure is a `StorageError` with `code` FULL / BLOCKED / CORRUPT / UNSUPPORTED_FORMAT and a readable message; callers (profile store, log store, version store, `useStored`, Settings) turn it into text, never a raw browser error. `createStore` keeps a full-but-readable `localStorage` instead of falling back to memory. `usage()` reports items and characters of this app's own keys; nothing is claimed about free space.
- **IndexedDB: UNCONFIRMED PROPOSAL, NOT BUILT, NOT MIGRATED.** Reason to consider it: `localStorage` is synchronous, text only and small (the limit was not measured here); imported versions already carry a 1,000,000-character cap and the log is capped at 1,000 entries. If chosen: add an `IndexedDbStore` implementing the SAME `KeyValueStore` interface (nothing above it changes); on first start copy each key from `localStorage`, read every copy back and compare it with the original; keep the `localStorage` data until that read-back has passed (and, if you want it, until you press a button); keep a read path for the old data; never delete first. Decisions needed from the user: (1) move everything or only the log and imported versions; (2) delete the old copy automatically after the read-back, or only on a button; (3) whether to ask the browser for persistent storage.

## Accessibility, focus and error handling (Chunk 15)
- **Focus** (`AppShell`, `DisclaimerGate`): the safety notice puts keyboard focus on its button when it opens; after a route change, and when the shell first appears (for example right after the notice), focus goes to `<main id="main" tabIndex={-1}>`; the "All screens" sheet takes focus when it opens, closes on Escape, and returns focus to the More button (a screen chosen in the sheet moves focus to the new screen instead). `main` and the sheet are focused by code only, never by Tab, so `theme.css` draws no ring around them. Before Chunk 15 focus was lost to `<body>` in all three cases (found by `tests/smoke-a11y.mjs`).
- **No error boundary exists** (checked: no `ErrorBoundary`, `componentDidCatch` or `getDerivedStateFromError` in `src/`). With React's default behaviour an error thrown while drawing is expected to leave a blank page; this was not provoked here. **UNCONFIRMED PROPOSAL, NOT BUILT:** one class component around `<App />` in `main.tsx` that, on an error, shows plain text ("The app stopped drawing this screen because of an unexpected error. Your stored data was not changed by this message. Reload to try again.") and ONE button, Reload. It would read no storage, delete nothing, offer no "reset", and keep the error text visible for copying. Needs your yes before it is added.
- **Wording audit** (`tests/smoke-wording.mjs`): the ban list is `complian`, `required fuel`, `permitted`, `must change`, `you must`, `tier iii` plus the VERDICT pattern of the other smoke tests. Exactly one sentence is excluded (the app disclaimer, which says "compliance" in a negation). Every other hit is printed and has to be on a reviewed list in the test; a new hit fails the test. The reviewed hits are all non-verdicts: the Changeover Calculator lead ("it is not a compliance statement"), the Vessel Profile completeness notes ("NOx compliance evidence cannot be confirmed"), and the engine tier choice label "Tier III".

## Area boundaries (Chunk 16, part A)
- Data flow: user file -> `previewImport` (kind `AREAS`; size cap, JSON, `parseAreaSet`) -> preview -> `commitImport` -> immutable stored version `setId@version` (`versions:AREAS:*`) -> explicit `activate` / `rollback` / confirmed `remove`. `resolveProductionAreas(store, confirmations, now)` in `services/versions/active.ts` re-parses the ACTIVE stored file on every read and returns `ProductionAreas` (`areas`, `items`, `set`, `key`, `verification`); `loadAll` carries it as `productionAreas`. Two active sets, a missing payload, or a stored file that no longer parses give `verification.state = "ERROR"` and NO areas.
- Parser (`services/areas/loader.ts`): pure, strict, whole-file refusal. Per area it adds `sourceReference`, `sourceDate` and free-text `notes` to the existing geometry parser (`calculations/geo/parse.ts`), so imported and DEMO areas are held to the same rules. No partial import: a boundary set missing an area could make a vessel look "outside" an area it is inside.
- Verification (`services/areas/confirmations.ts`): `UNVERIFIED` until a PERSON records a confirmation for that exact `setId@version` (name, time, fixed statement `AREA_CONFIRMATION_STATEMENT`); append-only under `areas:confirmations`; a new version is `UNVERIFIED` again; the file cannot confirm itself; an unreadable confirmation list means nothing counts as confirmed. The app records who said so; it cannot check the claim.
- Consumers: `hooks/usePrediction.ts` (imported areas join the bundled ones; REAL scope uses only non-DEMO areas; `areasUnverified` goes into `PredictionContext` and the panels show "VERIFY (AREA BOUNDARIES UNVERIFIED)"), `components/AlertsRunner.tsx` -> `calculations/alerts/engine.ts` (VERIFY with `AREA_DATA_UNVERIFIED` / `AREA_DATA_UNREADABLE`, never INSIDE ECA while unverified), `map/MapPanel.tsx` (draws the areas, UNVERIFIED / confirmed notice, source / set / verification on tap), `components/UpdateCenter.tsx` (import, version list, confirmation box). NOT consumers: `useSox`, `useNoxPm` (bundled data only on purpose; their REAL-scope note says so).
- Not covered: no boundary file is bundled; nothing was compared with the IMO text or the Marine Regions shapefile (parts B and C of the chunk); a real outline has never been loaded (only fictional TEST files); there is no Settings panel for the boundary design points (the Settings count stays eight).

## Area coverage flag (Chunk 16, part B2-2a, version 0.18.0)
- An area file (schema 2) declares `coverage` = COMPLETE or PARTIAL; schema 1 files count as PARTIAL (assumed). `parseAreaSet` carries `set.coverage` / `set.coverageAssumed`; `isPartialCoverage(set)` is the single test.
- `usePrediction` passes `areasPartial` (REAL scope, active set with areas, PARTIAL) into `predict` / `assessCurrentArea`; it is context only, the geometry result (INSIDE / OUTSIDE / BOUNDARY) is unchanged.
- `AlertsRunner` passes `areaData.coverage`. In `evaluateAlert` step 3, a geometry result OUTSIDE with a PARTIAL set (not ERROR, not DEMO) adds the DETERMINING reason `AREA_COVERAGE_PARTIAL` and gives VERIFY; it is never OUTSIDE or NORMAL, also for a CONFIRMED set. INSIDE a drawn area is still reported.
- Screens: import preview (Coverage row, notice), map (AREA SET PARTIAL notice, coverage in the area information), CURRENT AREA panel (no OUTSIDE wording), confirmed row. The app cannot check what a file declares.
